Instead of the expected 404 (previously), it now returns HTTP 500, confirming the soft-delete OR-pattern loadPendingItem now finds the row — but a LATER step in the approve pipeline crashes.

- **Environment**: Production on Render.com (Node.js server + MongoDB Atlas via Prisma)
- **Hypotheses (3-5 falsifiable)**:
  1. **updatePendingItem where-clause mismatch**: loadPendingItem now uses `OR: [{ deletedAt: null }, { deletedAt: { isSet: false } }]` and finds the row; but the corresponding `tx.studyMaterial.update({ where: { id: item.id }, ... })` ALSO still requires a strict `deletedAt: null` clause compounded into the where, causing Prisma to throw "Record not found for update" because the row's deletedAt is unset. Or the `updatePendingItem` uses `publicationStatus: PENDING_APPROVAL` without soft-delete isSet gating on the update where.
  2. **Missing relation select in loadPendingItem causes `.subject` / `.submittedBy` undefined**: loadPendingItem was recently modified and may no longer include `subject: { select: { id: true, name: true } }` / `submittedBy: { select: {...} }` relation in its Prisma select. The `buildNotification(item)` callback or `createResult(item)` then tries to access `item.submittedBy.id` / `item.subject.id` on undefined → TypeScript runtime TypeError: cannot read 'id' of undefined → express error handler returns 500.
  3. **Stale Prisma client on Render / schema mismatch**: This session also just added a new `explanation` field to BarFinalExamMcqQuestion model. If the Render deploy ran `prisma generate` but the deployed node_modules have a Prisma client generated AGAINST an older schema (pre-explanation), OR worse — prisma client was generated against the new schema BUT migration `prisma db push`/`prisma migrate deploy` was NOT executed against the actual Mongo Atlas cluster yet, creating schema drift. However this shouldn't affect StudyMaterial (law report) approving, so falsifiable by checking error mentions of MCQ/explanation.
  4. **Notification audience resolve function throws**: `buildNotification` queries a content admin user that no longer exists, or `findLatestContentAdminActor` function crashes because its bare `deletedAt: null` filter returns nothing and downstream code calls `.toString()` on a null result.
  5. **Approval audit log writer failure**: `tx.auditLog.create({...})` inside the transaction references userId from approverUser.id but approver is a super_admin with no User row OR AuditLog insert uses an enum value not in the schema.
